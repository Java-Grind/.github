18 вопросов для разговора, а не теста. Откройте карточку после своего ответа: внутри только ответ и объяснение того, как это работает.

01 / EQUALITY И HASHMAP

01Как связаны equals() и hashCode()?

Ответ. Если объекты равны по equals(), их hashCode() обязан совпадать; обратное неверно.

Объяснение. Одинаковый хеш не является уникальным ID: возможны коллизии. HashMap сначала выбирает бакет по хешу, затем сравнивает ключи через equals().

02Сколько null может хранить HashMap?

Ответ. Один ключ null и сколько угодно значений null.

Объяснение. Ключи уникальны: повторный put(null, value) заменит прежнее значение. ConcurrentHashMap не разрешает null ни для ключей, ни для значений.

03Что происходит при множестве коллизий в HashMap?

Ответ. Длинная цепочка элементов в бакете может стать красно-чёрным деревом.

Объяснение. Это снижает худший поиск с O(n) до O(log n). В Java 8+ переход зависит от длины цепочки и размера таблицы; это деталь реализации, не контракт API.

04Для чего нужен load factor?

Ответ. Он определяет, когда таблицу нужно увеличить.

Объяснение. При стандартном factor 0.75 у capacity 16 порог равен 12. Большее значение экономит память, но повышает вероятность коллизий.

05Почему HashMap не потокобезопасен?

Ответ. Параллельные изменения могут потерять данные или показать неконсистентное состояние.

Объяснение. put() состоит из нескольких действий: поиск бакета, изменение цепочки, иногда resize и публикация результата. Для конкурентной записи используйте подходящую синхронизацию или ConcurrentHashMap.

06Почему мутабельный ключ опасен для HashMap?

Ответ. Ключ может перестать находиться после изменения.

Объяснение. Если изменить поле из equals()/hashCode(), объект останется в старом бакете, а поиск начнётся по новому хешу. Выбирайте immutable-ключи: String, UUID, record.

07Когда возникает ConcurrentModificationException?

Ответ. При структурном изменении обычной коллекции во время fail-fast итерации не через сам итератор.

Объяснение. В одном потоке удаляйте через Iterator.remove() или removeIf. Исключение не является гарантией потокобезопасности.

02 / CONCURRENCY И JMM

08Что гарантирует volatile?

Ответ. Видимость изменений и ограничения упорядочивания, но не атомарность составных операций.

Объяснение. volatile boolean running подходит для флага. counter++ — это чтение, вычисление и запись, поэтому нужен AtomicInteger или синхронизация.

09Что означает happens-before для volatile?

Ответ. Запись в volatile-переменную happens-before последующему чтению этой же переменной другим потоком.

Объяснение. Это правило Java Memory Model обеспечивает наблюдаемость записанного состояния через volatile-флаг.

10Когда нужен synchronized, а когда volatile?

Ответ. volatile — для видимости простого состояния, synchronized — для связанных операций.

Объяснение. Проверка и изменение, например «если есть место, забронировать», должны выполняться атомарно; одного volatile здесь недостаточно.

11Чем ConcurrentHashMap отличается от HashMap?

Ответ. Он создан для безопасного конкурентного доступа.

Объяснение. Современная реализация использует CAS и локальную синхронизацию. Последовательность get() + put() всё равно не атомарна: для неё есть compute() и putIfAbsent().

12Чем Callable отличается от Runnable?

Ответ. Callable возвращает результат и может бросать checked exceptions.

Объяснение. Runnable.run() возвращает void. При отправке Callable в executor результат получают через Future.get().

13Чем shutdown() отличается от shutdownNow()?

Ответ. Первый метод не принимает новые задачи и ждёт уже поданные; второй запрашивает немедленную остановку.

Объяснение. shutdownNow() прерывает работающие потоки и возвращает невыполненные задачи, но задача должна сама корректно реагировать на interrupt.

03 / JAVA CORE И SPRING

14Чем overloading отличается от overriding?

Ответ. Overloading выбирается компилятором по параметрам; overriding — во время выполнения по реальному типу объекта.

Объяснение. Перегрузка — методы с одинаковым именем и разными списками параметров. Переопределение — новая реализация у подкласса; static, private и final методы не переопределяются.

15Что такое Dependency Injection в Spring?

Ответ. Контейнер передаёт зависимости объекту вместо того, чтобы объект создавал их сам.

Объяснение. Предпочтительна constructor injection: обязательные зависимости видны в сигнатуре и класс проще тестировать. В Spring Boot 3.x при единственном конструкторе @Autowired не нужен.

16Чем отличаются @Component, @Service и @Repository?

Ответ. Это стереотипы компонентов Spring с разной ролью.

Объяснение. Все находятся component scan. @Service обозначает бизнес-логику, @Repository — слой данных и перевод persistence-исключений, @Component — общий вариант.

17Что объединяет @SpringBootApplication?

Ответ. Конфигурацию, component scanning и auto-configuration.

Объяснение. Это композиция @SpringBootConfiguration, @EnableAutoConfiguration и @ComponentScan. Поэтому главный класс обычно размещают в корневом пакете.

18Чем BeanFactory отличается от ApplicationContext?

Ответ. BeanFactory — минимальный IoC-контейнер; ApplicationContext — более функциональная надстройка.

Объяснение. Контекст добавляет события, ресурсы, i18n, environment и обычную инфраструктуру Spring. В Spring Boot-приложении используют именно ApplicationContext.
